# 玩法设计：幕间卡牌交换

状态：核心规则已按用户描述实现第一版；文末列出的部分边界行为仍采用暂定方案，且尚未进行游戏内联机验证。

## 设计目标

在第一幕和第二幕结束后，让联机玩家互相交换卡牌。第三幕结束即结束本局，不触发交换。每次交换都由双方同意，并由双方各自选出一张非诅咒牌。

## 触发时机与阶段结束

1. 第一幕或第二幕结束时，等待本局所有玩家都选完该幕的卡牌奖励。
2. 全员完成奖励选择后，进入幕间交换阶段并显示交换界面。
3. 交换阶段结束后继续游戏；第三幕结束不进入此阶段。

## 请求与机会规则

- 每个幕间交换阶段，每位玩家有一次**成功发起交换**的机会。按此解释，第一幕和第二幕各自重置一次机会。
- 只有交换最终成功，才消耗发起者本阶段的机会。对方拒绝或请求超时都不消耗机会，发起者可再次发起，包括再次邀请同一玩家。
- 接受交换的一方不会因此消耗自己的主动发起机会，也可以成为多笔交换的接收方。
- 例如 A、B、C 三名玩家可依次完成 A→B、B→A、C→A：每个箭头表示左侧玩家发起，右侧玩家接收。A 可以收到多次请求；A 成功发起一次后仍可接收他人请求。
- 发起者选择另一位玩家昵称发送请求。接收者可以同意或拒绝。未在 **5 秒**内回应时，请求自动超时撤销；不交换卡牌，也不消耗发起者机会。请求双方都能看到逐渐耗尽的进度条和剩余秒数；主持端负责实际超时判定并广播结果。

## 选牌与提交

1. 接收方同意请求后，双方分别从**自己的整副牌组**中选择一张牌；诅咒牌不可选。
2. 双方各自确认所选卡牌后，才执行交换。任一方尚未确认时不得只转移一张牌。
3. 交换时保留卡牌原有状态。升级状态无需特殊处理，但交换前是什么状态，交换后仍是什么状态。
4. 提交前再次确认两张牌仍属于各自玩家且不是诅咒牌，并以联机安全的方式一次性完成双方牌组变更。

## 界面建议

- 使用独立交换面板，显示玩家昵称和可交换状态；点击昵称可向该玩家发起请求。
- 收到请求时提供“同意”和“拒绝”；请求界面显示 5 秒倒计时或明确的到期反馈。
- 双方选牌时显示牌组、当前选择、确认状态，以及等待对方确认的状态。
- 提供“跳过”按钮，供不想交换的玩家结束自己的交换操作。
- 跳过按钮显示全体玩家中的跳过人数，例如“跳过 2/3”；发起成功的玩家不计入跳过人数。

## 联机与安全约束

- 所有客户端的请求、接受/拒绝、选牌确认、超时和交换结果必须保持一致；不能只在某个客户端本地修改牌组。
- 应使用游戏或 BaseLib 提供的联机安全命令/消息流程。具体网络消息、命令和幕结束生命周期钩子必须先从当前游戏程序集或可验证的社区 API 确认，不可凭猜测实现。
- 交换提交应作为一个完整结果处理，避免一张牌已转移、另一张未转移的半完成状态。

## 尚待确认或实现前需定案

1. **跳过的作用范围**：当前建议将跳过解释为“放弃自己本阶段的主动发起机会并结束自己的操作”，但仍允许该玩家接收他人请求。若用户希望跳过后也不再接收请求，需要改成完全退出本阶段。
2. **并发请求**：当前建议同一时刻只处理一笔请求/选牌交易，完成或撤销后才能发起下一笔，以减少联机冲突。用户示例描述的是可先后完成三笔交易，未明确是否允许并行。
3. **交换阶段何时整体结束**：建议所有仍可发起请求的玩家都已成功发起或按跳过结束操作，且没有未完成请求/交易时结束；仍可接收请求的玩家在此规则下须维持可响应状态。
4. **选牌阶段断开或关闭界面**：用户只规定了请求的 5 秒响应期限；选牌确认阶段是否也需超时、取消或断线回滚，需要在实现前定案。

## 当前实现状态

- 已有纯 C# 规则协调器、Godot 覆盖层、BaseLib 消息类型和运行时接入代码。
- 卡牌选择改用游戏自带的牌组选牌屏幕，显示真实卡面网格、滚动和确认按钮；主持端仍会验证最终选择并广播权威流程结果。
- 目前暂定同一时间只允许一笔交易；跳过代表放弃本幕主动发起机会但仍可接收请求；只对请求回应设置 5 秒超时。
